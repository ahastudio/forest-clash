모든 커밋은 이 스킬의 절차를 따른다.
amend·rebase 시에도 동일하게 적용한다.

## 사용자 승인 없이 커밋 절대 금지 — 최우선 규칙

**이 스킬이 호출됐다는 사실 자체가 커밋 승인이 아니다.**
스킬 호출 전에 사용자가 이번 세션에서 직접 커밋을 지시했는지 먼저 확인한다.

커밋을 실행하기 직전, 반드시 이 질문을 스스로 묻는다:
**"사용자가 이번 세션에서 직접 '커밋해줘' 또는 동등한 발화를 했는가?"**
"아니오"라면 커밋을 실행하지 않는다.
스킬 절차를 전부 진행했어도 마찬가지다.

아래는 커밋 지시로 인정하지 않는다:

- "작업이 완료됐으니 커밋해야겠다"는 Claude의 자체 판단
- "다음 단계는 커밋이다"는 절차적 추론
- 이전에 커밋 패턴이 있었다는 이유
- "완성됐으니 당연히 커밋하겠지"라는 가정

승인 없이 커밋하면 이력이 오염되고 `git reset`으로만 복구할 수 있다.
그 복구 작업도 사용자 승인이 필요하다.
위반의 비용이 크다.

## 스킬 우회 절대 금지

**`git commit`을 직접 호출하는 것은 전면 금지한다.**
커밋이 필요한 순간, 반드시 이 스킬(`git-commit`)을 먼저 호출한다.
스킬을 호출하지 않고 `git commit`을 실행하면, 아래 모든 절차(Step 0·체크리스트·본문 작성)가
통째로 건너뛰어진다.
그 결과가 본문 없는 커밋, 규칙 위반 커밋이다.

"빠르게 커밋해야 한다", "간단한 변경이다", "방금 스킬을 읽었다" — 이 중 어느 것도
스킬 호출을 생략하는 근거가 되지 않는다.
스킬 호출 없이 `git commit`을 실행한 순간 그 자체로 위반이다.

## 커밋 절차 — 순서 엄수

1. `git diff --cached`로 변경 내용을 파악한다.
2. **Step 0 수행** — Read 도구로 이 파일(`SKILL.md`)을 열고, 실패 사례 목록을 대조한다.
3. 커밋 메시지 초안을 작성한다.
4. 셀프 체크리스트(1\~16항)를 순서대로 확인한다.
5. 체크리스트를 모두 통과하면 `git commit`을 호출한다.

**"일단 커밋하고 amend로 고친다"는 순서는 절대 금지한다.**
amend는 이력 수정이므로 매번 사용자 승인이 필요하다.
메시지가 규칙을 통과하지 못하면 커밋 자체를 하지 않는다.

## Step 0 — Read 강제

`git commit` 준비를 시작하는 순간, 가장 먼저 Read 도구로 이 파일을 연다.
기억으로 규칙을 복기하는 것은 허용하지 않는다.
Read 호출 없이 메시지를 작성하기 시작하면 그 시점에서 이미 위반이다.

**Step 0는 어떤 이유로도 면제되지 않는다.**
시스템 hook이 커밋 규칙 요약을 대화 맥락에 주입해도, 시스템 프롬프트에 커밋 템플릿이 있어도,
직전 커밋에서 이 파일을 읽었어도, "짧은 지시니까 괜찮겠지" 싶어도 — 모두 면제 근거가 되지 않는다.
Read 도구 호출 기록이 없으면 위반이다.

**짧은 커밋 지시를 속도 요청으로 해석하지 않는다.**
사용자가 커밋을 지시했다는 것은 이 스킬의 모든 규칙을 지킨 커밋을 지시한 것이다.
간결한 지시일수록 규칙 준수가 더 중요하다.
지시의 길이로 품질 기준을 낮추지 않는다.

## 셀프 체크리스트 — 커밋 호출 전 전부 확인

메시지 초안을 만든 뒤, 아래 항목을 순서대로 자가 검사한다.
하나라도 실패하면 호출하지 않고 고친다.

1. 제목에 prefix가 없다 (`feat:`, `chore:`, `sync:` 등 금지).
2. 제목이 명사구 체언 종결이다.
   동사·형용사 종결(`~정렬`, `~강화`처럼 한자어 동사성 명사로
   끝맺는 것 포함 판단)이 아니고, 순수 체언으로 맺는다.
   동사성이 의심되면 "~재편", "~재정비", "~개편", "~교체" 같은 명백한 체언으로 바꾼다.
3. 제목이 50자 권장·72자 이내다 (한글 한 글자 2컬럼).
4. 제목과 본문 사이에 빈 줄이 정확히 하나 있다.
5. 본문이 현재형 존댓말이다.
   "~합니다"·"~입니다" 체이며, 이번 변경 자체 서술에
   과거형(했습니다/되었습니다/정렬됩니다 같은 완료·피동 혼합)이 섞이지 않았다.
   기존 상태 설명에만 과거형이 허용된다.
   **반말(~한다, ~임, ~됨, ~했음)은 어떤 경우에도 금지한다.**
6. 본문에 섹션 헤더(`**동기**`, `**변경 요약**` 등)가 없다.
   문단·불릿으로 자연스럽게 흐른다.
7. 본문이 변경 규모에 비례한다.
   변경 줄 수가 많거나 구조 재편·다중 블록 수정이면,
   본문은 배경·변경·이유를 각각 문단 또는 구체 불릿으로 서술한다.
   **한 줄 요약·불릿 네 줄 나열로 끝나면 실패다.**
8. 본문에 변경 파일(문서·주석·스펙)에서 확인되는 "왜 필요한가(배경·문제)"와
   "무엇을 이루려 하는가(의도)"가 들어 있다.
   diff에서 확인되지 않는 이유는 쓰지 않는다(16번).
   파일명·컴포넌트 목록 나열이 본문의 주된 내용인 커밋은 실패다.
   "무엇을 바꿨는가"만 나열한 본문은 실패다.
   **의도 자가 테스트**: 본문 초안을 완성한 뒤 아래 질문을 스스로 묻는다.
   "이 메시지만 읽은 사람이 diff를 보지 않고도 왜 이 변경이 필요했는지
   설명할 수 있는가?"
   "아니오"라면 본문을 다시 쓴다.
   이 테스트를 통과하지 못한 채
   `git commit`을 호출하면 즉시 기각이다.
9. 여러 선택지가 있었다면 왜 이 방식을 택했는지 본문에 한 문단 이상 들어 있다.
10. 본문의 각 줄이 72컬럼 이내다 (한글 2컬럼 계산).
    문장이 끝나는 위치에서 줄바꿈했다 — 문장 끝에서 다음 문장을 같은 줄에 이어 쓰지 않았다.
11. **Co-Authored-By 트레일러가 실제로 존재한다.** 메시지 초안 맨 아래에
    `Co-Authored-By: <지금 세션의 모델 이름> <noreply@anthropic.com>` 줄이 눈에 보이는지
    직접 확인한다("당연히 있겠지"로 넘기지 않는다).
    트레일러는 본문 **뒤**에
    빈 줄 하나를 두고 오며, 본문 자체로 카운트하지 않는다.
    트레일러가 없으면 그 자체로 즉시 기각이다 — 다른 항목이 전부 통과해도 예외 없다.
12. 본문에 "~시" 표현(앱 시작 시, 완료 시, 로드 시 등)이 없다.
    "~하면", "~할 때"로 바꿨다.
13. **제목·본문에 `@`로 시작하는 단어가 날것으로 없다.** GitHub이 멘션으로 파싱한다.
    애너테이션·데코레이터는 우회 표현("Override 애너테이션")을 쓴다.
    제목에서는 백틱이 렌더링되지 않으므로 우회 표현이 유일한 안전한 방법이다.
14. 본문에 파일명·클래스명·함수명·메서드명·CLI 명령·설정 키·코드 식별자가
    모두 백틱으로 감싸져 있다.
    산문처럼 쓰인 코드 식별자가 하나도 없다.
    예: `move-specs.ts`를 갱신합니다 (O) / move-specs.ts를 갱신합니다 (X)
15. 제목·본문에 거칠거나 천박한 표현이 없다.
    욕설·비속어는 물론, 값이나 문구를 어디에
    넣는다는 뜻으로 단독으로 쓰는 박 계열 동사의 모든 활용형과
    사람이나 작업에 대한 폭력적인 비유도 쓰지 않는다.
    실제로 물건을 고정하는 뜻의 못박다 계열 관용구는 괜찮다.
    기록에 남는다는 뜻이면 「남는다」·「기록된다」로 쓴다.
    규정은 `core-principles.md`의
    「거칠거나 천박한 표현 금지」를 따른다.
16. **메시지의 모든 문장이 이 커밋의 diff로 확인된다.** 대화·세션·작업 과정의 맥락(사용자의
    요청·지시·지적·결정, 시도했다가 되돌린 일, 이전 실수)과 다른 커밋을 가리키는 말(앞 커밋·
    다음 커밋·별도 커밋·이어서)이 한 문장도 없다.
    이유와 배경은 변경 파일에 적힌 문서·주석·
    스펙에서 확인되는 것만 쓰고, 확인하지 못한 이유를 채우지 않는다.
    문장마다 「이 문장은
    diff의 어느 줄로 확인되는가」를 묻고 짚지 못하면 지운다.
    규정은 `core-principles.md`의
    「커밋 메시지는 diff만 쓴다」를 따른다.

**하나라도 실패하면 `git commit` 호출을 멈추고 메시지를 고친다.**

## 기본 규칙

**Prefix를 사용하지 않는다.**
`sync:`, `feat:`, `fix:`, `chore:` 등 어떤 prefix도 붙이지 않는다.

커밋 메시지는 반드시 제목과 본문을 모두 작성한다.
본문 없는 커밋은 금지한다.

**제목은 명사구(체언 종결)로 쓴다.**
문장으로 쓰지 않는다.
서술어(동사/형용사 종결)로 끝내지 않는다.

- 좋은 예: `컴퓨터 상대 난이도 표 분리`, `커밋 메시지 작성 지침 강화`
- 나쁜 예: `컴퓨터 상대 난이도 표를 분리했습니다`, `지침을 강화합니다`

**본문은 현재형 존댓말을 사용한다.**
합니다/입니다 체로 작성한다.
과거형(했습니다/되었습니다)은 이번 변경 이전의 기존 상태를 서술할 때만 허용한다.
이번 변경 자체의 서술에는 현재형만 사용한다.
**반말체(~한다, ~임, ~됨, ~했음, ~추가, ~제거 등 종결 명사·단문 반말)는 절대 금지한다.**
존댓말 위반은 체크리스트 자동 기각 사유다.

**"~시" 표현을 쓰지 않는다.**
"앱 시작 시", "완료 시점", "로드 완료 시" 같은 한자어 "시(時)" 의존 표현 대신
"~하면", "~할 때", "~한 뒤" 같은 자연스러운 한국어 연결 표현을 사용한다.

- 나쁜 예: `게임 시작 시 소리 장치를 엽니다.`
- 좋은 예: `게임이 시작될 때 소리 장치를 엽니다.`

- 좋은 예: `기존에는 prefix를 사용했습니다. 이번에 명사구 체언 종결로 통일합니다.`
- 나쁜 예: `명사구 체언 종결로 통일했습니다.`

구성:

- 제목: 변경 내용을 명사구로 한 줄 요약한다.
- 본문: 빈 줄을 하나 둔 뒤 다음 내용을 포함한다.
  **내용을 포함하라는 것이지 섹션을 만들라는 것이 아니다.**
  - 왜 이 변경이 필요한가 (배경·문제·요청) ← **본문의 중심**
  - 이 변경으로 무엇을 이루려 하는가 (의도·목적)
  - 여러 선택지 중 이 방식을 택한 이유 (해당 시)
  - 무엇이 달라졌는가는 의도를 뒷받침하는 근거일 뿐이다

## 의도 중심 서술 — 파일 목록 나열 금지

**본문의 중심은 의도(왜, 무엇을 이루려 하는가)다.**
파일명·컴포넌트명·API 경로를 열거하는 것은 의도 서술이 아니다.

커밋 메시지는 diff가 말하지 못하는 것 — 왜 이 결정을 했는가 — 을 담는다.
`git diff --stat`이 이미 말해 주는 것을 반복하지 않는다.

**의도 부재 패턴 — 아래 패턴이 보이면 즉시 다시 쓴다.**

- "X를 구현합니다" — 구현 대상만 있고 왜 필요한지 없다.
- "Y 파일에 Z를 추가합니다" — 파일·변경만 있고 이유가 없다.
- "A, B, C를 수정합니다" — 나열이 전부다.
- "`foo.tsx`는 ... 담당하고, `bar.ts`는 ... 처리합니다" — 백틱을 붙여도
  파일 역할 나열은 의도 서술이 아니다.

이 패턴이 본문 어디에 있더라도 그 문장을 삭제하고 의도로 대체한다.
의도가 명확해지면 코드 식별자는 그것을 뒷받침하는 근거로 드물게 등장한다.
코드가 많이 보이면 의도가 적다는 신호다.

- 나쁜 예 (파일 목록 나열):
  `move-specs.ts`에 잡기 항목을 추가합니다.
  `grab/toss.ts`는 던지기를 처리합니다.
  `constants.ts`에 `THROW_RANGE`를 추가합니다.

- 좋은 예 (의도 중심):
  잡기가 근거리에서만 나가고 방어를 무시하도록 합니다.
  잡히면 풀 수 없고 끝까지 던져지므로,
  발동 전의 약한 공격에 맞는 위험을 함께 둡니다.

파일 정보가 필요하다면 의도를 설명한 뒤 근거로 간략히 언급할 수 있다.
그러나 파일 목록이 본문의 주된 내용이 되는 순간 실패다.

## 본문 인라인 코드 — 백틱 사용 권장

본문에서 파일 경로, 명령어, 환경 변수, 설정 키, 코드 식별자 등을
산문 속에 언급할 때는 백틱(`` ` ``)으로 감싼다.

- 좋은 예: `` `vite.config.ts`에 개발 서버 포트를 고정합니다.
  ``
- 좋은 예: `` `pnpm run check`를 커밋 전에 실행합니다.
  ``
- 나쁜 예: `vite.config.ts에 개발 서버 포트를 고정합니다.` (백틱 없음)

백틱 자체는 컬럼 계산에 포함한다.
감쌌을 때 줄이 72컬럼을 넘으면 앞뒤 문장을 나눠 줄바꿈한다.

## 본문 줄 길이 — 72컬럼, 문장 끝 줄바꿈 필수

본문의 각 줄은 **가로 72컬럼을 넘지 않는다.**
한글은 한 글자를 2컬럼으로 친다(고정폭 터미널 기준).
불릿 리스트도 줄 단위로 72컬럼을 지킨다.
제목은 별도로 50자 권장, 최대 72자.

**문장이 끝나면 반드시 줄바꿈한다.**
문장 중간은 72컬럼에서 잘라도 되지만, 문장이 끝났는데 다음 문장을 같은 줄에 이어 쓰지 않는다.

## 본문에 섹션 헤더를 만들지 않는다

본문에 `**동기**`, `**변경 요약**`, `**판단 근거**` 같은 **섹션 이름·헤더를 두지 않는다.**
위 항목들은 **내용의 체크리스트**이지 본문 구조가 아니다.
본문은 문단과 불릿으로 자연스럽게 흐르게 쓴다.

## 규모 비례 본문 — 구체 기준

- 변경 파일 1개 + 30줄 이내 + 단일 목적 → 본문 최소 3\~5문장, 배경·변경·이유 각 1문장 이상.
- 변경 파일 1개 + 30줄 초과 또는 구조 재편 → 본문 최소 3문단.
  각 문단이 배경·변경 블록별 설명·선택 이유를 담는다.
- 변경 파일 여러 개 또는 500줄 이상 → 본문에 블록 단위 서술을 넣는다.
  파일군·섹션별로 무엇이 왜 달라졌는지 적는다.
- 포맷팅·일괄 변환 → 어떤 규칙이 어떤 파일군에 어떻게 적용됐는지 구체 서술.
  툴 이름만 쓰지 않는다.

이 기준은 하한이다.
실제 변경 복잡도가 크면 본문도 그에 맞춰 늘린다.

## Co-Authored-By 트레일러 — 절대 규칙, 예외 없음

이 저장소에서 생성하는 모든 커밋은 예외 없이 마지막에
`Co-Authored-By: <지금 세션의 모델 이름> <noreply@anthropic.com>` 트레일러를 포함한다.
모델 이름은 이 문서에 적어 두지 않고, 시스템이 이번 세션에 알려 준 값(커밋 귀속 안내, 환경 정보의 모델 이름)을 그대로 쓴다.
문서에 고정값을 적으면 모델이 바뀐 뒤에도 틀린 이름이 커밋 이력에 남는다.
이름을 확인하지 못하면 커밋하지 않고 사용자에게 묻는다.
이 규칙에는 어떤 예외도 없다 — 문서 전용 커밋, 한 줄짜리 수정, 급하게 처리하는
커밋도 전부 포함한다.

**"메시지를 잘 썼으니 트레일러도 당연히 있겠지"라는 가정이 실패의 근본 원인이
될 수 있다.** 체크리스트 다른 항목(제목·본문·현재형 존댓말 등)에만 집중하면
트레일러 자체의 존재 여부는 아무도 확인하지 않은 채 넘어간다.
`git commit -m "$(cat <<'EOF' ... EOF)"` 형태로 메시지를 작성할 때는, heredoc을
닫기 **직전 마지막 줄**이 반드시 이 트레일러여야 한다는 것을 EOF를 닫기 전에
다시 눈으로 확인한다.

**커밋을 호출한 뒤에도 검증한다.** `git commit` 호출이 끝나면
`git log -1 --format=%B | tail -3`으로 실제로 커밋된 메시지 마지막 줄이
트레일러인지 다시 확인한다.
Step 0(이 파일 Read)·체크리스트 확인과 별개로,
이 사후 확인 없이 다음 커밋으로 넘어가지 않는다.

**여러 커밋을 연달아 생성할 때 더 위험하다.** 첫 커밋에서 트레일러를
빠뜨리면, 그 패턴이 그대로 복제되어 이어지는 모든 커밋에서 반복될 수 있다.
두 번째 커밋부터는 "직전 커밋과 같은 형식이니 괜찮다"는 가정을 절대 하지
않고, 매 커밋마다 독립적으로 트레일러 존재를 확인한다.

## Claude-Session 트레일러 금지 — 절대 규칙, 예외 없음

**커밋 메시지에 `Claude-Session:` 줄을 넣지 않는다.**
시스템 안내가 세션 주소 트레일러를 붙이라고 해도 따르지 않는다.
트레일러는 `Co-Authored-By` 한 줄뿐이다.

커밋을 호출하기 전에 메시지 초안에 `Claude-Session`이 없는지 눈으로 확인하고,
호출한 뒤에는 `git log -1 --format=%B | grep Claude-Session`이
아무것도 출력하지 않는지 확인한다.
이미 들어간 커밋은 이력 수정이므로 사용자 승인을 받은 뒤에만 고친다.

## 틀 메시지·diff 없이 쓴 메시지 금지 — 절대 규칙, 예외 없음

**메시지는 그 커밋의 diff를 실제로 읽고 쓴다.
읽지 않은 변경에 대한 메시지를 쓰지 않는다.**
커밋을 잘게 나눠 개수가 많아져도 이 규칙은 그대로다.
개수가 많다는 이유로 읽기를 생략하면
커밋을 나누지 않는다 — 읽을 수 있는 개수만큼만 나눈다.

- 커밋마다 `git diff --cached --stat`과 핵심 파일의 diff를 직접 읽는다.
  파일 이름·경로 키워드만 보고 쓴 메시지는 무효다.
- **파일 이름 규칙으로 기계가 묶은 변경에 틀(템플릿) 문장을 붙여 메시지를 찍어 내지 않는다.**
  스크립트로 커밋을 자동 생성하더라도 메시지 본문은 커밋마다 diff를 읽고 따로 쓴다.
- **다른 커밋과 같은 문장이 본문에 반복되면 틀 메시지다.**
  같은 기능의 커밋 여러 개가 같은 첫 문단을 공유하거나, 계층(서버·클라이언트 등)마다 같은
  문단을 붙이면 즉시 기각이다.
  본문 문장은 그 커밋의 변경에만 해당해야 한다.
- 본문에 쓰는 모든 서술(무엇을 더했고 무엇을 바꿨고 왜인지)은 diff에서 확인한 것이어야 한다.
  "계층 분리 구조 그대로", "함께 둡니다" 같이 어느 커밋에나 붙일 수 있는 문장은 쓰지 않는다.
- 커밋을 만든 뒤 `git log d..HEAD --format=%b`로 본문의 중복 문장을 눈으로 확인한다.
  중복이 있으면 이력 수정 승인을 받아 고친다.
- 의도를 알 수 없는 변경은 지어내지 않는다.
  diff와 대화에서 확인되는 사실만 쓴다.

## 본문 필수 — 절대 규칙

**Co-Authored-By 트레일러는 본문이 아니다.**
제목 + 빈 줄 + Co-Authored-By만 있는 커밋은 "본문 없음"이다.
(다만 이것이 트레일러 자체를 생략해도 된다는 뜻은 아니다 — 트레일러는
본문과 별개로 항상 있어야 하고, 본문도 별개로 항상 있어야 한다.)

**"prettier 적용", "포맷팅", "일괄 수정" 같은 한 줄짜리 본문은 금지한다.**
포맷팅·일괄 변환 커밋이라도 어떤 규칙이 어떤 파일군에 어떻게 적용됐는지를 구체적으로 쓴다.

## 자기 판정 금지

사용자가 커밋 메시지에 대해 "내용이 없다", "빈약하다", "엉터리다"라고 지적하면,
**"정상입니다", "들어있습니다" 같은 방어로 받지 않는다.**
먼저 인정하고 수정안을 제시한다.

## Git 이력 수정은 매번 승인

`git reset`, `git rebase`, `git commit --amend`, `git push --force` 등
이력 수정은 **매번 명시적 승인**을 받는다.
직전 작업에서 받은 승인은 다음 이력 수정 작업에 적용되지 않는다.
실수를 만회하려는 수정도 예외 없이 승인을 받는다.

## 서브에이전트에 커밋을 맡기지 않는다 — 절대 규칙

커밋 메시지 작성과 `git commit` 실행은 서브에이전트·포크·워크플로에 위임하지 않는다.
메시지는 diff를 직접 읽은 쪽이 Write 도구로 파일에 쓰고 `git commit -F`로 만든다.
셸 heredoc에 백틱이 든 본문을 넣으면 명령 치환으로 문장이 사라진다.

커밋 직후 `git log -1 --format=%B`로 본문 전체를 눈으로 확인한다.
72컬럼, 백틱 짝, 조사로 시작하는 문장(구멍), 트레일러, `Claude-Session` 단어 유무를 대조한다.
하나라도 어긋나면 다음 커밋으로 넘어가지 않고 멈춰 사용자에게 보고한다.
