# 코딩 스타일

게임 코드(`src/`의 테스트가 아닌 파일)에 적용한다.
테스트 코드의 기준은 `testing.md`다.

## 도구가 지키게 하는 것

아래는 `pnpm run check`가 어기면 실패시킨다.
도구가 지켜 주는 것을 눈으로 다시 따지지 않는다.

- 모든 문장은 세미콜론으로 끝난다.
  작은따옴표, 두 칸 들여쓰기, 한 줄 120컬럼, 후행 쉼표는 Biome가 맞춘다.
- `any`와 `!`(non-null 단언)를 쓰지 않는다.
- 쓰지 않는 변수·인자·import를 남기지 않는다.
- 모든 제어문에 중괄호를 쓴다(`useBlockStatements`).
- 한 함수의 인지 복잡도는 10 이하다.
- 타입 검사는 `strict`이고, 인덱스 접근은 `undefined`일 수 있는 값으로 본다.
- JSDoc은 문서화 대상(export한 선언과 그 공개 멤버)에만 쓰고 한 줄로 쓰지 않는다(`check_jsdoc.cjs`가 구문 트리로 잡는다).

## 역할을 섞지 않는다

- `src/engine/`은 순수 로직이다.
  화면, 소리, 브라우저 객체(`document`, `window`), 현재 시각, 무작위를 부르지 않는다.
  입력을 받아 상태를 바꾸고, 일어난 일은 사건(`events`)으로 내보낸다.
- 화면(`src/render/`)과 소리(`src/audio/`)는 엔진의 상태와 사건을 보여 줄 뿐이다.
  규칙을 화면 코드에서 판정하지 않는다.
- 컴퓨터 상대(`src/ai/`)는 사람과 같은 입력(방향과 버튼 네 개)만 낸다.
  엔진의 상태를 직접 바꾸지 않는다.
- 규칙의 설명과 수치는 기능 문서(`specs/`)와 같아야 한다.
  수치를 바꾸면 기능 문서와 테스트를 같은 변경에서 맞춘다.

## 이름

- 이름만 보고 무엇인지 알 수 있어야 한다.
  줄임말과 범용 단어(`data`, `tmp`, `val`)를 쓰지 않는다.
- 변수·함수·필드는 `camelCase`, 상수는 `UPPER_SNAKE_CASE`, 타입은 `PascalCase`다.
- 캐릭터를 가리키는 변수는 `fighter`처럼 풀어 쓴다.
- 프레임 수, 거리, 속도 같은 숫자는 이름 있는 상수로 둔다.
  기술의 프레임 데이터는 기술 표(`move-specs.ts`와 갈래별 `move-specs-*.ts`)에만 쓴다.

## 함수

- `if`·`else`·`for`·`while`·`do` 등 모든 제어문은 중괄호를 쓰고, 여는 중괄호 뒤에서 줄을 바꾼다.
  본문이 한 문장이어도 마찬가지다.
  `if (조건) return;`처럼 한 줄에 쓰지 않는다.
- 함수 본문은 문장 5개 이하로 쓴다.
  넘으면 함수를 나눈다.
  여러 줄에 걸친 문장은 1개로 세고, 닫는 중괄호와 빈 줄은 세지 않는다.
  `if (조건) {` 한 줄과 그 안의 `return;`은 각각 1개씩이므로 가드 절은 2개다.
- 함수 인자는 3개 이하다.
  이 숫자는 읽기 쉬운지를 가늠하는 지표이지 기계적으로 맞출 목표가 아니다.
  인자를 받는 방식은 호출하는 자리에서 읽히는가로 정한다.
  - 호출하는 자리에서 값의 뜻이 드러나지 않으면 인자가 하나여도 이름 있는 객체로 받는다.
    불리언 플래그, 같은 타입의 숫자나 문자열이 이웃한 경우가 대표적이다.
  - 좌표나 쿼터니언(x, y, z, w)처럼 순서가 곧 뜻인 값은 넷이어도 그 순서대로 받는다.
  - 그리기 도구(`g`)나 월드 같은 문맥은 첫 인자로 두고 이름 있는 객체에 넣지 않는다.
  - 함께 다니는 값은 객체로 묶고, 개수만 줄이려고 배열이나 이름 없는 모음에 숨기지 않는다.
- `if`·`while`의 조건식과 삼항 연산자의 조건은 한 줄에 들어가는 짧은 식이다.
  길어지면 이름 있는 변수나 함수로 추출해 `if (isReachable(strike))`처럼 읽히게 쓴다.
  조건식을 여러 줄로 나누어 쓰지 않는다.
- 조건이 맞지 않으면 일찍 돌려보내는 가드 절을 쓴다.
  `else if` 사슬과 중첩된 `if`·`else`를 쓰지 않는다.
  두 갈래를 고르는 것뿐이면 삼항 연산자나 `else` 하나는 허용한다.
- 갈래가 많으면 조건문을 늘어놓지 않고 표(객체)로 고른다.
  예: 상태별 갱신 함수 표, 사건별 반응 표, 기술별 자세 표.
- 같은 코드가 세 번째로 나오면 추출한다.

## 객체와 타입

- 객체의 값을 한꺼번에 바꿀 때는 `Object.assign` 대신 `src/patch.ts`의 `patch`를 쓴다.
  바꿀 값의 이름과 형식을 컴파일러가 검사하므로, 이름을 바꾸는 작업이 안전하다.
- 이름이나 형식을 바꿀 때는 에디터의 이름 바꾸기(언어 서비스)를 쓴다.
  문자열 검색과 치환으로 바꾸지 않는다.
- 값이 없을 수 있는 자리에 기본값(`?? 0`)을 습관으로 붙이지 않는다.
  없을 수 없는 값이면 타입으로 없을 수 없게 만들고, 없을 수 있는 값이면 없을 때의 동작을 테스트로 확인한다.
- 필드가 많은 타입(`Fighter`)은 관심사별 인터페이스(`FighterBody`, `FighterAction`, `InputTracking`, `FighterReactions`)를 합친 것으로 쓴다.
  기본값을 만드는 함수도 같은 인터페이스를 돌려주어, 필드 목록을 타입과 함수에 이중으로 적지 않는다.
- `as` 단언은 컴파일러가 알 수 없는 사실이 있을 때만 쓰고, 그 근거를 주석으로 적는다.

## 응집

- 한 규칙의 입력, 조건, 진행, 결과는 한 폴더에 모은다.
  예: 잡기는 `src/engine/grab/`에 있다.
  규칙 하나를 바꾸려고 여러 파일을 오가야 하면 응집이 약한 것이다.
- 파일은 300줄 이하로 둔다.
  넘으면 갈래별로 나누고 기존 진입점의 이름과 내보내는 값은 바꾸지 않는다.
- 이름, JSDoc, 테스트가 있는데도 읽기 어렵다면 이름이나 설명이 부족한 것이다.
  함수를 나누면 읽기 어렵다는 이유로 나누기를 미루지 않는다.
- 이 절의 기준을 어긴 곳을 찾을 때는 검색 결과를 후보로만 보고, 후보마다 호출하는 자리에서 읽히는지 사람이 읽어 판단한다.

## 쓰레기 코드는 금지한다

- 쓰이지 않는 변수, 함수, export, 파일, 의존성을 남기지 않는다.
- 주석 처리된 코드와 디버그 잔재(`console.log`, `debugger`)를 남기지 않는다.
- 같은 함수 본문을 복사해 두지 않는다.
- 점수나 줄 수를 맞추려고 의미 없는 래퍼, 이름, 주석을 만들지 않는다.
- 상세와 점수 기준은 `quality-score.md`다.

## TypeScript

- `typescript`는 5.x이고 7은 쓰지 않는다. 의존성을 다루는 규칙은 `dependencies.md`다.

## 확인

- 코드를 고친 뒤 `pnpm run check`를 실행해 통과를 확인한다.
  이 명령은 TypeScript 버전 검사(`guard`)와 품질 점수(`score`)를 포함한다.
- 코드나 설계를 고친 뒤에는 보고하기 전에 항상 `pnpm run score`로 점수를 계산하고, 기준(95점) 아래이거나 내려갔으면 먼저 고친다.
- 엔진이나 컴퓨터 상대를 고쳤으면 테스트가 통과하는 것에 더해, 같은 입력에서 같은 결과가 나오는지(`src/regression.test.ts`)를 본다.
  결과가 달라지는 것이 의도한 변경일 때만 그 테스트의 기대값을 고치고, 고친 이유를 커밋 메시지에 적는다.
- 화면을 고치면 개발 서버에서 실제 화면을 눈으로 확인한다.

## 주석과 JSDoc

주석을 쓰기 직전마다 스스로 묻는다: 「이것은 이 선언을 쓰는 쪽이 읽는 문서인가?」
맞으면 JSDoc이고, 아니면 `//` 일반 주석이다. 문서화할 만한 내용이 못 되는 것을 JSDoc으로 꾸미지 않는다.

- JSDoc 대상은 export한 함수, 클래스, 타입, 인터페이스, 상수와 그 공개 멤버(`private`과 `protected`가 아닌 것)다. `export { ... }`로 내보내는 것도 같다.
  무엇을 하는지, 인자와 반환, 쓰는 쪽이 알아야 할 조건을 쓴다.
- 그 밖의 모든 설명은 `//` 일반 주석이다.
  export하지 않은 선언, `private`·`protected` 멤버, 함수 본문 안, 시험 코드, 검사 스크립트의 내부 함수, 구현의 이유나 주의를 적는 메모가 여기에 든다.
- JSDoc은 한 줄로 쓰지 않는다.
  내용이 한 문장이어도 항상 `/**`, ` * 내용`, ` */` 세 줄 이상으로 쓴다.
  한 줄짜리 JSDoc(`/** 내용 */`)은 어떤 자리에서도 쓰지 않는다.
- 파일 맨 위의 소개 블록은 파일을 소개하는 문서이므로 JSDoc 형식으로 둔다.
  `@type`처럼 형식 검사 도구가 읽는 태그는 제자리에 둔다.
- 이름을 되풀이하거나 내용이 없는 JSDoc은 쓰레기 주석이다. 점수를 맞추려고 채우지 않는다.
- 점검은 `pnpm run guard`의 `_agent/checks/check_jsdoc.cjs`다. 구문 트리로 문서화 대상이 아닌 자리의 JSDoc과 한 줄 JSDoc을 잡고, `node _agent/checks/check_jsdoc.cjs --fix`가 고친다.
  점검 통과가 판단을 대신하지 않는다. 새 주석은 쓰기 전에 위 질문으로 정한다.
- 이 규칙을 어긴 주석을 발견하면 누가 썼든 그 자리에서 고치고, 같은 유형이 더 있는지 전수 검사한다.
