# Findings & Decisions

> **기술적 발견, 중요한 결정이 있을 때마다 이 파일을 즉시 업데이트하세요.**

## Requirements

- 타이틀에서 컴퓨터 대전, 같은 컴퓨터 둘이서 대전, 온라인 대전 중 하나를 고른다.
- 온라인 대전은 구글 로그인 후 서버에서 상대를 찾아 겨루고 승패를 기록한다.
- 서버는 계정 관리, 승패 기록, 매칭을 맡고 `server/` 폴더 하나에 Go로 만든다.
- 순위표, 친구와 방 만들기, 관전, 채팅은 이 기능의 범위가 아니다.

## Research Findings

### 코드베이스 구조

- `src/engine`은 무작위와 현재 시각을 부르지 않는다. 프레임마다 받는 입력은 방향 네 개와 버튼 네 개(8비트)이므로 같은 입력이면 같은 결과가 나온다.
- `src/engine/flow.ts`: 타이틀에서 1P가 버튼을 새로 누르면 컴퓨터 대전, 2P만 누르면 둘이서 대전을 시작한다. 타이틀이 나온 지 20프레임이 지나야 받는다.
- `src/game.ts`: 입력을 읽어 엔진을 한 프레임 진행한다. 모바일 조이스틱도 같은 키보드 입력을 쓴다.

### 기존 패턴

- 화면 코드는 엔진의 상태를 읽기만 한다. 메뉴와 온라인 상황도 `View`에 담아 읽는다.
- 갈래가 많으면 조건문을 늘어놓지 않고 표로 고른다. 서버 메시지 읽기(`PARSERS`)와 처리(`handlers`)도 표로 둔다.
- 브라우저 객체(웹소켓, 구글 로그인 스크립트)는 바깥에서 주입받아 테스트에서 가짜로 바꾼다.

## Technical Decisions

| Decision | Rationale |
| -------- | --------- |
| 두 브라우저가 같은 엔진을 돌리고 서버는 입력만 전달한다 | 엔진이 같은 입력에 같은 결과를 내므로 서버가 게임을 계산할 필요가 없고 서버가 간단해진다 |
| 입력 지연 락스텝으로 동기화한다 | 상태를 저장하고 되감는 롤백보다 구현이 작다. 느린 쪽에 맞춰 멈추는 약점은 입력 지연으로 줄인다 |
| 내 입력을 6프레임 뒤의 번호로 보낸다 | 게임이 초당 45프레임(속도 0.75배)으로 돌아가 6프레임은 약 133밀리초로, 상대 입력이 도착할 시간을 벌어 멈춤을 줄이기 위해 |
| 승패는 두 사람의 보고가 같을 때만 기록한다 | 서버가 게임을 계산하지 않으므로 한 사람의 거짓 보고를 막는 가장 간단한 방법이다 |
| 판 도중 한쪽이 나가면 남은 사람의 승으로 기록한다 | 이기고 있던 사람이 상대의 이탈로 기록을 잃지 않게 하기 위해 |
| 같은 계정의 동시 접속을 거절한다 | 대기열에서 자기 자신과 만나는 일을 없애기 위해 |
| 계정은 구글 `sub`로 구분하고 이메일은 저장하지 않는다 | 필요한 것은 계정 구분뿐이므로 개인 정보를 모으지 않기 위해 |
| 서버 저장은 JSON 파일 하나로 시작하고 저장소 인터페이스 뒤에 둔다 | 계정과 승패 두 가지뿐이라 데이터베이스가 아직 필요 없고, 나중에 바꿀 수 있게 하기 위해 |
| 서버를 게임 저장소의 `server/`에 둔다 | 프로토콜을 한 변경에서 고치고 문서와 함께 관리하기 위해. 배포는 게임(정적)과 서버(Go)를 따로 한다 |
| 타이틀 메뉴는 키보드가 아니라 마우스와 화면 터치(포인터 입력)로 누른다 | 컴퓨터와 모바일이 같은 입력 하나로 동작하고, 모바일에서 조이스틱으로 버튼을 옮기는 단계를 없애기 위해 |
| 버튼 위의 커서는 항상 손가락 모양이다. 타이틀의 캔버스 버튼은 프레임마다 그릴 때 정하고, 화면 조작 버튼은 스타일, 로그인 창의 취소 버튼은 만들 때 지정한다 | 캔버스 위의 버튼은 마우스가 움직이지 않아도 단계가 바뀌면(대전 시작) 커서가 바뀌어야 하므로 이벤트가 아니라 그릴 때 정한다 |
| 타이틀 메뉴는 정사각형에 가까운 버튼 세 개를 가로로 놓고 글자는 줄을 바꿔 쓴다 | 한 줄에 쓰면 긴 글자(「같은 컴퓨터에서 둘이서」)가 버튼을 가로로 길게 만들어, 세 개를 한 줄에 균형 있게 놓기 어렵다 |
| 구글 로그인은 stub을 먼저 만들고 같은 자리(`signIn`)에 나중에 구글을 끼운다 | 구글 클라이언트 아이디 없이 로컬에서 로그인, 매칭, 대전, 기록 전체를 바로 눈으로 확인하기 위해(바깥에서 안으로 만든다) |
| stub 토큰은 서버가 `AUTH_STUB`을 켰을 때만 받는다 | stub은 누구나 아무 이름으로 들어올 수 있으므로 기본은 꺼 두고 로컬에서만 켜기 위해 |
| 클라이언트의 stub과 서버 주소 기본값은 개발 서버에서만 쓴다 | 빌드한 결과물이 의도하지 않게 stub으로 동작하지 않게 하기 위해 |
| 서버 주소(`VITE_SERVER_URL`)의 출처를 보안 정책(CSP) 연결 허용에 자동으로 더한다(`vite.config.ts`의 `server-connection`) | 서버가 게임과 포트가 달라 같은 출처('self')가 아니고, 주소를 환경 값으로 받으므로 정책에 미리 적을 수 없기 때문에. 값이 없으면 정책을 바꾸지 않는다 |
| 개발용 서버는 전용 스크립트로만 켜고 끄며, 서버 포트를 쓰는 프로세스 중 실행 폴더가 서버 폴더인 것만 끈다 | 같은 컴퓨터에서 다른 프로세스가 포트를 쓸 수 있으므로, 이름으로 찾아 끄면 이 서버가 아닌 것을 끌 수 있기 때문에. 실행 폴더는 심볼릭 링크를 풀어 실제 경로로 비교한다 |
| 서버 포트는 게임 개발 서버 포트에 1을 더한 58970이다 | 같은 컴퓨터의 다른 서버와 겹치지 않고 두 포트의 관계를 기억하기 쉽게 하기 위해 |
| 타이틀 뒤의 싸움은 실제 엔진과 따로 도는 연습용 엔진으로 한다 | 실제 엔진은 타이틀에서 캐릭터를 움직이지 않으며, 규칙을 바꾸지 않고 그대로 재사용할 수 있고, 온라인 대전의 동기화에 영향을 주지 않기 위해 |
| 연습용 엔진은 가장 쉬운 난이도에 체력을 채워 K.O.가 나지 않게 하고 소리는 내지 않는다 | 가볍게 싸우는 배경으로 보이고, 타이틀 위의 글자와 버튼보다 눈에 띄지 않게 하기 위해 |
| 타이틀 시작은 엔진을 바꾸지 않고 엔진이 받는 버튼 입력을 만들어 준다 | 시작 규칙(타이틀 지연, 시작 소리)을 엔진 한 곳에 두기 위해 |
| 서버 통신 코드는 `src/online/web-socket.ts` 한 곳에만 둔다 | 보안 점검이 네트워크 API를 한 파일로 한정해 다른 곳의 통신을 위반으로 잡게 하기 위해 |
| 보안 정책의 연결 허용은 `wss:`(암호화된 연결 전체)와 로컬 개발 서버(`ws://localhost:*`)로 연다 | 서버 주소를 환경 값으로 받으므로 빌드 전에는 호스트를 알 수 없고, 로컬에서는 암호화 없이 접속하기 때문에. `index.html`과 `vercel.json`이 같은 값을 쓴다 |
| 창 격리 정책을 팝업 허용 값(`same-origin-allow-popups`)으로 바꾼다 | 구글 로그인 창이 열린 뒤 결과를 돌려주려면 팝업과의 통신이 막히면 안 되기 때문에 |
| 상대 입력을 기다리는 동안 안내 글자를 띄우지 않는다 | 짧은 멈춤마다 글자가 깜빡여 오히려 거슬리기 때문에. 왕복 시간은 따로 핑으로 보인다 |
| 진행하지 못한 프레임의 시간을 돌려받아 따라잡는다. 한 틱에 4프레임, 쌓는 시간은 100밀리초까지 | 돌려받지 않으면 멈출 때마다 그 시간이 사라져 게임이 계속 느려진다. 한도가 없으면 오래 멈춘 뒤 빨리 감기듯 진행한다 |
| 핑은 서버가 보낸 시각을 그대로 돌려주는 `ping`/`pong`으로 잰다. 서버는 상태를 갖지 않는다 | 클라이언트가 보낸 시각과 받은 시각만 있으면 왕복 시간을 알 수 있어 서버에 기억할 것이 없다 |
| 핑은 1초마다 재고 새 값을 30퍼센트만 반영한 평균으로 보인다 | 숫자가 프레임마다 흔들려 읽을 수 없는 것을 막기 위해 |
| 핑은 서버까지의 왕복이다. 상대와의 거리는 따로 재지 않는다 | 입력은 서버를 거쳐 가므로 서버와의 왕복이 느린 이유가 내 연결인지 알려 주는 가장 간단한 값이다 |
| 온라인 대전을 시작할 때 남은 연결을 먼저 닫는다(`start`) | 상대가 나가면 서버의 기록을 받으려고 연결을 열어 두는데, 그대로 다시 시작하면 같은 계정의 새 연결이 거절된다 |
| 구글 토큰의 표시 이름은 stub 이름과 같은 규칙으로 거른다(제어 문자 제거, 앞뒤 공백 제거, 32글자) | 이름은 사용자가 정한 값이고 상대 화면에 그대로 그려지므로 길이와 제어 문자를 믿지 않는다 |
| 구글 공개 키를 가져오지 못해도 이미 받은 키를 쓰고 가져오기는 1분에 한 번만 시도한다 | 구글의 일시적인 장애가 모든 로그인을 막지 않게 하고, 장애 중에 로그인마다 느린 요청이 이어져 서버가 막히지 않게 하기 위해서다 |
| 만료되었거나 60초 안에 만료되는 토큰은 다시 쓰지 않는다 | 구글 ID 토큰은 한 시간쯤 뒤에 만료되는데 접속할 때마다 처음 받은 토큰을 쓰면 오래 켜 둔 뒤의 접속이 오류로 끝나기 때문이다 |
| 구글 로그인 창은 어두운 배경 위에 게임 분위기의 카드(초록 바탕, 금색 테두리)를 놓고 구글 버튼은 구글이 그리는 그대로 둔다 | 구글 버튼의 모양은 구글이 정하므로 바꿀 수 없고, 버튼을 둘러싼 창만 게임의 다른 화면과 어울리게 하기 위해 |
| 결과를 보고한 사람이 나가면 승패를 기록하지 않는다 | 보고하지 않은 쪽이 보고를 미루고 기다리면, 이긴 사람이 나가는 순간 진 사람의 승으로 기록되기 때문이다. 기록하지 않으면 그런 이득이 없다 |
| 한 접속이 1초에 보내는 메시지는 150개까지, 동시 접속은 2000개까지 받는다 | 게임은 초당 45프레임이라 입력과 ping을 합쳐도 훨씬 적게 보낸다. 한도가 없으면 한 사람이 입력을 쏟아 상대의 전송 줄을 채워 접속을 끊게 할 수 있다 |
| 로그인 실패 이유는 정해 둔 오류만 사용자에게 보내고 나머지는 서버 로그에만 남긴다 | 키를 가져오지 못한 오류에 구글 주소와 네트워크 오류가 들어 있어 로그인 전 접속에도 그대로 나갔기 때문이다 |
| 저장소에 쓰는 동안 허브의 잠금을 풀고, 바뀐 것이 없는 로그인은 저장하지 않는다 | 로그인마다 파일 전체를 쓰며 잠금을 쥐면 한 계정의 반복 접속이 모든 사람의 입력 중계를 멈추게 하기 때문이다 |
| 저장 파일을 `os.Root`로 연 폴더 안에서만 다룬다 | 파일 경로를 직접 쓰면 심볼릭 링크로 폴더 밖을 건드릴 수 있고 `gosec`이 경로 조작(G703, G304)으로 보고하기 때문이다. 폴더를 열지 못하면 시작하지 않는다 |
| 승패 기록도 판을 끝난 것으로 표시한 뒤 잠금 밖에서 저장하고, 서버를 끌 때 `Hub.Close`로 허브를 닫고 기다린다 | 기록을 저장하는 동안 잠금을 쥐면 다른 판의 입력 중계가 멈추고, 끄는 신호에 저장이 잘리면 기록이 사라지기 때문이다. 저장에 실패하면 판을 다시 기록할 수 있게 되돌린다. 웹소켓 접속은 `Shutdown`이 기다려 주지 않아 닫은 뒤에 끝나는 판이 있을 수 있으므로, 닫은 허브는 그 판을 따로 돌리지 않고 그 자리에서 기록해 기다리는 도중에 새 기록이 더해지지 않게 한다 |
| 저장 파일은 임시 파일에 쓰고 디스크에 내려보낸(`fsync`) 뒤 이름을 바꾼다 | 이름 바꾸기만으로는 전원이 꺼질 때 내용이 디스크에 닿기 전에 이름만 바뀌어 비어 있는 저장 파일이 남을 수 있기 때문이다 |
| 표시 이름에서 서식 문자(글자 방향을 바꾸는 문자, 폭이 없는 문자)도 지운다 | 제어 문자 검사만으로는 이런 문자를 걸러내지 못해 상대 화면의 이름이 다르게 보일 수 있기 때문이다 |

## Issues Encountered

### 1. 온라인 대전이 끝난 뒤 컴퓨터 대전 도중 타이틀로 돌아간다

**문제**:

온라인 대전이 오류로 멈춘 뒤 컴퓨터 대전을 시작하면 매 프레임 타이틀로 돌아간다.

**원인**:

「온라인 흐름이 멈췄으면 남은 판을 닫는다」는 검사가 온라인 판이었는지 따지지 않았다.

**해결**:

온라인 판을 시작했는지(`inOnlineMatch`)를 따로 기억해, 그 판일 때만 닫는다.

**결과**:

`game-online.test.ts`의 「온라인이 끝난 뒤 컴퓨터와 하는 판은 타이틀로 돌아가지 않는다」가 확인한다.

### 2. 기록된 뒤 상대가 나가면 내 기록 문구가 지워진다

**문제**:

두 사람이 결과 화면에서 거의 동시에 타이틀로 돌아올 때, 먼저 나간 쪽의 이탈 알림이 늦게 돌아온 쪽의 「내 기록」 문구를 「상대가 나갔습니다」로 덮는다.

**원인**:

서버는 연결이 닫히면 항상 이탈을 알리는데, 이미 기록된 판의 이탈은 정리일 뿐이다.

**해결**:

승패가 기록된 뒤의 이탈 알림은 무시한다(`recorded`).

**결과**:

`session.test.ts`가 기록 뒤의 이탈에서 문구가 유지되는지 확인한다.

### 3. 알림 처리를 `switch`로 쓰면 린트와 점수 기준에 걸린다

**문제**:

서버 메시지마다 처리를 `switch`로 고르면 값을 돌려주지 않는 함수가 값을 돌려준다는 린트 오류가 나고, 함수 본문이 문장 5개를 넘는다.

**원인**:

메시지 종류마다 처리를 `switch`의 갈래로 늘어놓는 구조가 린트의 반환 검사와 함수 문장 수 기준에 걸린다.

**해결**:

메시지 종류마다 처리를 표(`handlers`)로 고르고, 표에서 꺼낸 처리를 모든 메시지를 받는 함수로 보는 단언을 근거 주석과 함께 한 곳에 둔다.

**결과**:

린트와 품질 점수(100점)를 통과한다.

### 4. 상대가 나간 뒤 다시 온라인 대전을 고르면 이미 접속 중인 계정이라고 나온다

**문제**:

상대가 접속을 끊어 타이틀로 돌아온 뒤 「온라인 대전」을 누르면 「이미 접속 중인 계정입니다」가 뜬다.

**원인**:

상대가 나가면 서버의 기록을 받으려고 연결을 열어 둔다(`stop`). 게임은 타이틀로 돌아오지만 연결을 닫는 `finish()`는 정상 종료 때만 불린다. 서버는 연결이 끊기기 전까지 계정을 접속 중으로 두므로 새 연결이 거절된다.

**해결**:

`start()`가 새로 접속하기 전에 남은 연결을 닫는다. 닫은 연결의 닫힘 알림이 늦게 와서 새 접속을 끊지 않도록, 지금 연결의 알림만 받는다.

**결과**:

`session.test.ts`가 재시작, 취소 뒤 재시작, 늦은 닫힘 알림을 확인한다. 켜 둔 서버에 스크립트로 접속해 낡은 연결을 연 채로는 거절되고 닫은 뒤에는 `ready`를 받는 것을 확인했다.

### 5. 검사를 돌릴 때마다 열려 있는 게임 화면이 새로고침된다

**문제**:

`pnpm run check`를 돌릴 때마다 개발 서버 로그에 `page reload coverage/...`가 수십 줄 찍히고, 열려 있는 게임 화면이 새로고침되어 온라인 연결이 끊긴다.

**원인**:

검사가 다시 쓰는 `coverage/`의 파일을 개발 서버가 소스 변경으로 보았다.

**해결**:

`vite.config.ts`의 감시 제외(`server.watch.ignored`)에 `coverage`, `dist`, `server`, `infra`를 더했다.

**결과**:

개발 서버를 다시 켠 뒤 `pnpm run check`를 돌려도 새로고침이 0건이다.

### 6. 새 메시지를 모르는 옛 서버가 오류로 답해 대전이 끝난다

**문제**:

핑을 더한 화면이 `ping`을 보내자 켜 둔 옛 Go 서버가 「알 수 없는 메시지입니다」로 답했고 화면은 오류를 받아 대전을 끝냈다.

**원인**:

서버를 다시 켜지 않아 `ping`을 모르는 옛 바이너리가 떠 있었다. 화면은 오류 메시지를 항상 치명적으로 본다.

**해결**:

서버를 새 코드로 다시 켰다. 배포할 때 서버를 먼저 배포하는 순서는 `../server-infra/`에 적었다.

**결과**:

켠 서버가 `ping`에 같은 시각의 `pong`으로 답하는 것을 확인했다.

### 7. 구글 로그인의 결함 네 가지

**문제**:

구글 로그인 스크립트를 한 번 불러오지 못하면 다시 시도해도 계속 실패한다. 구글 공개 키를 가져오지 못하면 받아 둔 키가 있어도 모든 로그인이 실패한다. 구글 이름이 길이와 제어 문자 검사 없이 상대에게 보인다. 오래 켜 둔 뒤에는 만료된 토큰으로 접속해 오류로 끝난다.

**원인**:

스크립트를 불러오는 약속(Promise)을 한 번 만들어 계속 재사용해 실패한 약속도 남는다. 키를 가져오는 쪽은 만료된 캐시를 버리고 가져오기가 실패하면 오류를 돌려준다. 표시 이름 거르기는 stub 이름에만 있었다. 토큰은 처음 로그인한 것을 만료와 상관없이 다시 썼다.

**해결**:

스크립트를 불러오기에 실패하면 약속을 지우고 실패한 태그도 지운다. 키 캐시는 가져오기에 실패하면 받아 둔 키를 쓰고 시도 간격을 1분으로 제한한다. 이름 거르기를 `shortName`으로 모아 구글과 stub에 같이 쓴다. 토큰의 만료 시각(`exp`)을 읽어 만료되었거나 60초 안에 만료되면 다시 로그인한다.

**결과**:

서버와 클라이언트 테스트가 네 가지를 확인하고 커버리지와 정적 분석을 통과한다. 실제 구글 로그인으로도 접속해 확인했다.

### 8. 보안 점검이 서버 통신 코드를 위반으로 잡는다

**문제**:

`pnpm run security`가 웹소켓으로 서버와 통신하는 코드를 위반으로 잡는다.

**원인**:

보안 점검이 게임 코드의 네트워크 API 사용을 모두 금지했고, 서버와 통신하는 코드를 허용하는 자리가 없었다.

**해결**:

서버 통신을 `src/online/web-socket.ts` 한 파일에서만 허용하도록 점검의 허용 파일(`NETWORK_FILE`)을 더했다.

**결과**:

보안 점검이 통과하고, 다른 파일에서 통신하는 코드는 위반으로 잡힌다.

### 9. 서버를 읽어 찾은 보안 결함 아홉 가지

**문제**:

결과를 보고한 사람이 나가면 보고하지 않은 상대의 승으로 기록된다. 로그인한 사용자가 입력을 속도 제한 없이 보내 상대의 접속을 끊게 하거나 상대 브라우저의 메모리를 늘릴 수 있다. 바뀐 것이 없는 로그인도 저장하며 허브의 잠금을 쥔다. 로그인 오류의 원문(구글 주소, 네트워크 오류)이 로그인 전 접속에 나간다. 접속 수 제한이 없다. 표시 이름에 글자 방향을 바꾸는 문자가 남는다. 컨테이너 실행 옵션과 이미지 고정이 없다. 임시 로그인이 https 출처와 함께 켜져도 시작된다.

**원인**:

이탈 처리가 보고 여부를 보지 않고, 입력 중계와 접속에 한도가 없었다. 저장소 로그인이 변경 여부와 상관없이 저장했고 허브가 그동안 잠금을 쥐었다. 로그인 오류를 `err.Error()` 그대로 보냈고, 이름 거르기는 제어 문자(`unicode.IsControl`)만 봤다.

**해결**:

보고한 사람의 이탈은 기록하지 않는다. 접속당 초당 메시지 150개와 동시 접속 2000개, 프레임 번호 상한(2의 24제곱)을 두고, 클라이언트는 지나갔거나 36000프레임보다 먼 상대 입력을 버린다. 접속 상태를 먼저 잡은 뒤 잠금을 풀고 저장하며, 이름이 같은 로그인은 저장하지 않고, 저장은 임시 파일을 디스크에 내려보낸 뒤 이름을 바꾼다. 정해 둔 오류만 사용자에게 보내고 나머지는 로그에 남긴다. 서식 문자도 지운다. 컨테이너는 읽기 전용, 권한 전부 제거, 새 권한 금지, 메모리 256MB, 프로세스 256개로 실행하고 기본 이미지를 다이제스트로 고정한다. 임시 로그인은 https 출처와 함께 켜면 시작하지 않는다.

**결과**:

서버 시험이 각 항목을 확인하고, 옵션을 켠 컨테이너가 `/healthz`에 응답하며 `/data`에는 쓰고 그 밖에는 쓰지 못하는 것을 확인했다.

## Learnings

### 같은 입력이면 같은 결과가 나오는 엔진은 입력만 전달하면 된다 (2026-10-21)

엔진이 무작위와 시각을 부르지 않으므로 서버가 상태를 계산하지 않아도 두 브라우저가 같은 판을 본다.
그래서 서버가 간단해지고 동기화의 정확성은 엔진의 결정성에 기댄다. 엔진에 무작위나 시각을 넣으면 이 방식이 깨진다.

### 브라우저 객체는 주입해서 시험한다 (2026-10-21)

웹소켓과 구글 로그인 스크립트는 바깥에서 받아 쓰므로 실제 네트워크 없이 흐름 전체를 단위 테스트로 확인한다.

### 락스텝에서 늦은 입력은 어긋남이 아니라 멈춤이다 (2026-10-23)

두 화면은 같은 프레임의 두 입력이 모여야 진행하므로 입력이 늦어도 상태가 달라지지 않고 멈출 뿐이다.
멈춘 시간을 따로 처리하지 않으면 그 시간만큼 게임이 느려지므로, 시간을 돌려받아 따라잡는다.
핑은 시각(`now`)을 주입해 시계를 움직이며 간격과 평균을 시험한다.

### 한 명이 해 보는 온라인 시험은 상대 역할이 필요하다 (2026-10-23)

대전은 두 사람의 입력이 모여야 진행한다. 상대가 없으면 멈춘 채로 보이므로, 대기열에 들어가 아무것도 누르지 않은 입력을 보내는 상대 스크립트를 붙여 시험한다.
브라우저를 조작하는 도구의 키 입력은 눌렀다 바로 떼므로 프레임마다 키를 읽는 게임은 놓친다. 키를 일정 시간 누르고 있는 이벤트로 시험한다.

### 실패한 결과를 캐시하지 않는다 (2026-10-24)

한 번만 불러오려고 약속(Promise)을 저장해 두면 실패한 약속도 함께 저장되어 다시 시도해도 계속 실패한다.
저장하는 것은 성공한 결과뿐이어야 하고, 실패하면 저장한 것을 지워 다음 시도가 새로 시작하게 한다.
